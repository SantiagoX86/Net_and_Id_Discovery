## 1. Purpose

The Output Artifact Retention Specification defines the governed Milestone M10 capability for preserving generated framework output artifacts without overwriting prior run results.

M10 introduces a controlled enhancement to file-output artifact handling so each discovery execution with file output enabled creates timestamped, retained artifacts in designated output subdirectories.

The intended model is:

```text
authorized discovery execution
→ governed run result
→ timestamped JSON run artifact
→ timestamped Markdown report artifact
```

The preferred generated artifact layout is:

```text
<output-dir>/
  results/
    discovery_run_YYYYMMDD_HHMMSSZ.json

  reports/
    discovery_report_YYYYMMDD_HHMMSSZ.md
```

If no `--output-dir` is supplied, the existing CLI default output directory remains the current working directory, resulting in:

```text
./results/discovery_run_YYYYMMDD_HHMMSSZ.json
./reports/discovery_report_YYYYMMDD_HHMMSSZ.md
```

This specification replaces the prior PDF-oriented M10 direction.

M10 no longer introduces a standalone PDF report interface, PDF rendering dependency, or separate `wauig-report-pdf` command.

## 2. Supersession Statement

This document supersedes the prior M10 PDF Report Interface Specification.

The prior PDF-oriented model is retired for M10 because the underlying product issue is output artifact overwrite risk, not lack of PDF rendering.

The approved M10 scope is now:

```text
Output Artifact Retention Enhancement
```

The approved M10 implementation target is preservation of generated JSON and Markdown artifacts through timestamped filenames and designated artifact subdirectories.

## 3. Architectural Boundary Statement

Output Artifact Retention is a controlled enhancement to local generated artifact handling.

The capability supports preservation of existing governed output formats without changing discovery behavior, finding semantics, output meaning, or runtime module behavior.

M10 MUST:

* Preserve existing discovery behavior
* Preserve existing inference behavior
* Preserve existing correlation behavior
* Preserve existing orchestration behavior
* Preserve existing `DiscoveryFinding` schema behavior
* Preserve JSON serialization semantics
* Preserve Markdown report generation semantics
* Preserve `--no-files` behavior
* Preserve authorized CLI execution flow
* Use timestamped filenames to avoid routine overwrite of generated artifacts
* Store JSON run artifacts under a `results/` subdirectory
* Store Markdown report artifacts under a `reports/` subdirectory
* Derive the artifact timestamp from the run context timestamp
* Create required artifact subdirectories when file output is enabled
* Fail closed rather than overwrite an existing timestamped artifact path

M10 MUST NOT:

* Introduce new discovery capability
* Introduce new discovery ports
* Introduce new protocol interaction
* Open sockets beyond existing validated discovery behavior
* Add authentication, negotiation, enumeration, banner grabbing, response parsing, or TLS inspection
* Modify target systems
* Add inference rules
* Add correlation rules
* Modify existing discovery, inference, or correlation domains
* Modify the `DiscoveryFinding` schema
* Emit new findings as part of artifact retention
* Suppress, deduplicate, merge, normalize, reclassify, reinterpret, or semantically reconcile findings
* Introduce PDF generation
* Introduce a PDF rendering dependency
* Introduce a standalone report post-processing command
* Introduce a historical run database
* Introduce multi-run comparison or trend analysis
* Treat retained JSON artifacts as a cumulative logging subsystem

## 5. Known Output-Retention Limitation Being Addressed

The existing discovery execution path writes fixed generated output filenames when file output is enabled:

```text
discovery_run.json
discovery_report.md
```

When the same output directory is reused across discovery executions, these fixed filenames may overwrite prior generated artifacts.

This creates a practical retention issue for:

* Engineering validation
* Operator review
* Portfolio evidence
* Audit traceability
* Before-and-after comparison workflows
* Repeated controlled lab executions

M10 addresses this limitation by creating timestamped JSON and Markdown artifacts in designated output subdirectories.

M10 does not change what the framework discovers, infers, correlates, serializes, or reports.

M10 changes only where and how generated output artifacts are written when file output is enabled.

## 6. Output Artifact Model

### 6.1 Parent Output Directory

The existing `--output-dir` argument remains the parent output directory for generated artifacts.

If the operator supplies:

```bash
wauig-discovery --target <authorized-target> --output-dir <output-directory>
```

then M10 writes generated artifacts under:

```text
<output-directory>/results/
<output-directory>/reports/
```

If the operator does not supply `--output-dir`, the current working directory remains the parent output location, resulting in:

```text
./results/
./reports/
```

### 6.2 JSON Results Directory

Machine-readable JSON run artifacts MUST be written under:

```text
<output-dir>/results/
```

The generated JSON filename MUST use the format:

```text
discovery_run_YYYYMMDD_HHMMSSZ.json
```

Example:

```text
results/discovery_run_20260707_174512Z.json
```

### 6.3 Markdown Reports Directory

Human-readable Markdown report artifacts MUST be written under:

```text
<output-dir>/reports/
```

The generated Markdown filename MUST use the format:

```text
discovery_report_YYYYMMDD_HHMMSSZ.md
```

Example:

```text
reports/discovery_report_20260707_174512Z.md
```

### 6.4 Shared Artifact Timestamp

The JSON and Markdown artifacts generated from the same discovery execution MUST share the same timestamp string.

The timestamp string MUST be derived from the run context timestamp:

```text
DiscoveryContext.run_started_at
```

The implementation MUST NOT generate separate independent timestamps for the JSON and Markdown artifact filenames.

This ensures both artifacts remain traceable to the same execution.

### 6.5 Timestamp Format

The timestamp string MUST use UTC and the following format:

```text
YYYYMMDD_HHMMSSZ
```

Example:

```text
20260707_174512Z
```

The timestamp MUST be derived from the UTC-normalized run start time.

### 6.6 Overwrite Protection

The implementation MUST NOT overwrite an existing timestamped artifact.

If a generated artifact path already exists, the implementation MUST fail closed with a controlled error rather than overwrite the file.

This applies to both JSON and Markdown artifacts.

### 6.7 Directory Creation

When file output is enabled, the implementation MUST create the required `results/` and `reports/` directories if they do not already exist.

Directory creation MUST occur only for local filesystem artifact output.

Directory creation MUST NOT imply remote storage, cloud storage, database storage, or external integration behavior.

## 7. Relationship to Existing Runtime Behavior

### 7.1 Discovery Runtime

M10 does not alter the approved discovery runtime execution chain.

The approved orchestrated execution behavior remains unchanged.

M10 does not add, remove, reorder, suppress, or modify runtime modules.

### 7.2 CLI / Control Layer

The CLI remains responsible for controlled operator input handling, execution context construction, orchestrator invocation, and local file-output handling.

M10 may update CLI file-writing behavior to support timestamped artifact retention.

The CLI MUST remain free of discovery, inference, correlation, and semantic reporting business logic.

The CLI MUST NOT reinterpret findings when writing retained artifacts.

### 7.3 Output / Reporting Layer

The Output / Reporting Layer remains responsible for JSON serialization and Markdown report generation.

M10 does not redefine JSON content semantics.

M10 does not redefine Markdown report content semantics.

M10 may rely on existing output/reporting functions to generate the JSON-serializable run structure and Markdown report content.

M10 artifact retention behavior concerns file naming, directory placement, and overwrite protection.

### 7.4 Generated Artifact Meaning

The retained JSON artifact remains the machine-readable run record.

The retained Markdown artifact remains the human-readable report.

Neither artifact is a cumulative operational log.

Each artifact pair represents one discovery execution.

## 8. Repository Hygiene Model

Generated output artifacts are local run artifacts and MUST NOT be committed to the repository unless explicitly promoted as governed validation evidence.

M10 implementation SHOULD update repository hygiene controls if necessary to prevent routine generated artifacts from appearing as untracked project source files.

At minimum, repository hygiene SHOULD consider excluding root-level generated artifact directories:

```text
/results/
/reports/
```

If validation uses a custom output directory, that directory SHOULD also remain uncommitted unless explicitly promoted as test evidence.

## 10. Determinism Requirements

M10 implementation MUST preserve deterministic behavior wherever applicable.

The implementation MUST:

* Use a fixed artifact directory model
* Use a fixed filename prefix for JSON artifacts
* Use a fixed filename prefix for Markdown artifacts
* Use a fixed UTC timestamp format
* Use the same run-derived timestamp for both artifacts
* Write artifacts in a predictable order
* Avoid random filenames
* Avoid environment-dependent naming beyond the operator-selected parent output directory
* Avoid adaptive behavior based on finding content

The content of generated JSON and Markdown artifacts remains governed by existing output/reporting functions.

---

## 11. Error Handling Expectations

M10 implementation MUST fail safely and clearly when artifact output cannot be completed.

Controlled error handling MUST apply when:

* Parent output path is invalid
* Required subdirectory cannot be created
* JSON artifact path already exists
* Markdown artifact path already exists
* JSON artifact cannot be written
* Markdown artifact cannot be written

Error handling MUST NOT result in partial silent success.

If one artifact write succeeds and the second fails, the implementation must surface a controlled error.

The implementation SHOULD avoid overwriting or deleting previously generated artifacts during failure handling.
