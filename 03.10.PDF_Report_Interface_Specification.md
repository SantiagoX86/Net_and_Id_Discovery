## 1. Purpose

The PDF Report Interface Specification defines the governed Milestone M10 capability for producing timestamped local PDF reports from existing governed discovery output artifacts.

M10 introduces a minimal standalone interface-layer report-consumption capability.

The intended model is:

```text
existing discovery execution
→ existing discovery_run.json
→ standalone PDF report interface
→ timestamped PDF report artifact
```

The preferred command concept is:

```bash
wauig-report-pdf --input discovery_run.json --output-dir pdf_reports
```

The preferred generated PDF naming convention is:

```text
discovery_report_YYYYMMDD_HHMMSSZ.pdf
```

Example:

```text
pdf_reports/discovery_report_20260706_171245Z.pdf
```

This specification governs the architectural boundary, input/output contract, PDF retention model, rendering expectations, dependency governance, validation requirements, and acceptance criteria for the PDF report interface.

This specification does not implement M10. Implementation must occur in a separate implementation activity after this specification is reviewed and accepted.

## 2. Architectural Boundary Statement

The PDF Report Interface is an interface-layer capability that consumes existing governed framework output artifacts and renders them into timestamped local PDF documents for human review and report retention.

The PDF Report Interface MUST:

* Consume an existing `discovery_run.json` artifact as read-only input
* Produce a local timestamped `discovery_report_YYYYMMDD_HHMMSSZ.pdf` artifact
* Write generated PDF reports to a dedicated operator-specified or default PDF output directory
* Preserve governed output meaning
* Preserve all producer-owned fields, evidence values, controlled vocabularies, timestamps, and target values as represented in the source JSON
* Remain standalone from the orchestrated discovery runtime
* Remain outside the discovery, inference, correlation, orchestration, control, and deployment layers
* Preserve M1–M9 validated behavior
* Improve human-readable PDF report retention without redesigning existing discovery-output behavior

The PDF Report Interface MUST NOT:

* Execute discovery
* Register as an orchestrated runtime module
* Invoke the `DiscoveryOrchestrator`
* Instantiate discovery, inference, or correlation domains
* Modify `DiscoveryFinding`
* Emit `DiscoveryFinding` records
* Introduce new discovery behavior
* Introduce new discovery ports
* Introduce new protocol interaction
* Open sockets
* Probe targets
* Authenticate
* Negotiate protocols
* Parse target responses
* Perform banner grabbing
* Perform TLS handshakes
* Perform inference
* Perform correlation
* Perform enrichment
* Perform risk scoring
* Perform prioritization
* Perform semantic reconciliation
* Alter orchestration behavior
* Alter existing JSON or Markdown output semantics
* Change the existing `wauig-discovery` output filename behavior
* Mutate, suppress, deduplicate, normalize, reclassify, reinterpret, merge, collapse, or semantically reconcile findings
* Treat PDF formatting, sections, tables, headings, or summaries as the authoritative technical source of truth

The source `discovery_run.json` remains the authoritative technical source of truth for the run consumed by the PDF interface.

The generated PDF is a human-readable interface artifact intended to improve report readability and PDF retention.

## 4. Known Output-Retention Limitation Being Addressed

The existing discovery execution path writes fixed generated output filenames when file output is enabled:

```text
discovery_run.json
discovery_report.md
```

This means that when the same output directory is reused across discovery executions, the existing JSON and Markdown runtime artifacts may be overwritten.

This limitation is recognized as a late-stage record-retention concern.

M10 addresses this concern at the interface layer by producing timestamped PDF report artifacts in a dedicated PDF output directory.

M10 does not redesign, replace, or alter the previously validated discovery output behavior.

The M10 resolution is:

```text
Known limitation:
Existing discovery runtime artifacts use fixed filenames and may be overwritten if the same output directory is reused.

M10 resolution:
The standalone PDF interface creates timestamped PDF report artifacts in a dedicated PDF output directory, preserving human-readable report history without altering existing discovery runtime behavior.
```

This approach preserves M1–M9 freeze protections while improving practical human-readable report retention for portfolio, audit, review, and operator-use purposes.

## 5. Relationship to Existing Domains and Layers

### 5.1 Network Discovery Domain

Network Discovery remains the authoritative producer of Network-owned findings and evidence fields.

The PDF Report Interface MUST NOT alter Network Discovery behavior, Network-owned categories, Network-owned evidence fields, port inventory, service classification, timeout behavior, or connect-only interaction model.

The PDF Report Interface may display Network findings exactly as represented in `discovery_run.json`, but MUST NOT reinterpret Network findings or treat Network findings as replacements for findings from other producing domains.

### 5.2 Identity Discovery Domain

Identity Discovery remains the authoritative producer of identity-related direct-observation findings and Identity-owned governed evidence values.

The PDF Report Interface MUST NOT alter Identity Discovery behavior, port scope, output categories, evidence fields, service hints, or discovery-only responsibility boundary.

The PDF Report Interface may display Identity findings exactly as represented in `discovery_run.json`, but MUST NOT perform identity classification or reinterpret Identity findings.

### 5.3 Application / Service Discovery Domain

Application / Service Discovery remains the authoritative producer of bounded application/service direct-observation findings and Application / Service-owned governed evidence values.

The PDF Report Interface MUST NOT alter Application / Service Discovery behavior, approved port scope, output categories, evidence fields, service hints, or discovery-only responsibility boundary.

The PDF Report Interface may display Application / Service findings exactly as represented in `discovery_run.json`, but MUST NOT perform application classification, product identification, protocol validation, or semantic enrichment.

### 5.4 Telemetry / Logging Exposure Discovery Domain

Telemetry / Logging Exposure Discovery remains the authoritative producer of bounded telemetry/logging direct-observation findings and Telemetry / Logging-owned governed evidence values.

The PDF Report Interface MUST NOT alter Telemetry / Logging behavior, approved port scope, output categories, evidence fields, service hints, or discovery-only responsibility boundary.

The PDF Report Interface may display Telemetry / Logging findings exactly as represented in `discovery_run.json`, but MUST NOT access, retrieve, parse, or infer logging content.

### 5.5 Host Configuration Discovery Domain

Host Configuration remains the authorized inference-only consuming domain for host-level posture inference.

The PDF Report Interface MUST NOT recreate Host Configuration inference rules, duplicate Host Configuration logic, perform posture inference, modify Host Configuration findings, or produce derived host posture findings.

The PDF Report Interface may display Host Configuration findings exactly as represented in `discovery_run.json`.

### 5.6 Correlation Domain

Correlation remains the authorized correlation-only consuming capability for cross-domain relationship analysis.

The PDF Report Interface MUST NOT recreate correlation rules, duplicate correlation logic, perform relationship analysis, modify Correlation findings, or emit correlation-owned findings.

The PDF Report Interface may display Correlation findings exactly as represented in `discovery_run.json`.

### 5.7 Core Framework / Orchestration Layer

The Core Framework remains orchestration-only.

The PDF Report Interface MUST NOT alter the Core Framework contract, orchestrator sequencing, module registration, aggregation behavior, failure isolation behavior, or finding schema.

The PDF Report Interface MUST NOT register as a `DiscoveryModule`.

### 5.8 CLI / Control Layer

The existing `wauig-discovery` CLI remains the approved execution path for discovery runs.

The PDF Report Interface may define a separate post-processing command for local PDF rendering:

```bash
wauig-report-pdf --input discovery_run.json --output-dir pdf_reports
```

This command is not a discovery command and MUST NOT accept discovery execution inputs such as `--target`.

The PDF Report Interface command MUST NOT invoke the discovery CLI, construct a `DiscoveryContext`, or execute the orchestrator.

### 5.9 Output / Reporting Layer

The existing Output / Reporting Layer remains responsible for generating governed JSON and Markdown artifacts.

The PDF Report Interface consumes the already-generated JSON artifact after the Output / Reporting Layer has completed.

The PDF Report Interface MUST NOT alter existing JSON serialization semantics or Markdown report semantics.

The PDF artifact is an interface-layer rendering of existing governed JSON output. It does not replace the Output / Reporting Layer and does not redefine output meaning.

### 5.10 Deployment Layer

The Deployment Layer remains responsible for packaging, installation, dependency declaration, environment readiness, and operational readiness.

M10 implementation may require additive packaging metadata updates to declare an approved PDF rendering dependency and console entry point.

Packaging changes MUST remain deployment-oriented and MUST NOT introduce discovery, inference, correlation, orchestration, control, or reporting business logic.

## 6. Interface Model

### 6.1 Interface Type

The PDF Report Interface is a standalone local command-line post-processing interface.

The interface consumes a local file path pointing to an existing governed `discovery_run.json` artifact and writes a timestamped local PDF report file.

### 6.2 Preferred Command Concept

The preferred command concept is:

```bash
wauig-report-pdf --input discovery_run.json --output-dir pdf_reports
```

### 6.3 Approved Inputs

The interface may accept only the following operator inputs:

| Input | Required | Purpose |
| --- | --- | --- |
| `--input` | Yes | Path to an existing governed `discovery_run.json` artifact |
| `--output-dir` | No | Directory where timestamped PDF report artifacts are written |

If `--output-dir` is not provided, the implementation MAY use a controlled default output directory:

```text
pdf_reports
```

The default output directory decision must be finalized during implementation and documented in README after validation.

### 6.4 Optional Explicit Output Filename

The minimal preferred model is output-directory based, with implementation-owned deterministic timestamped filename generation.

An explicit `--output` filename is not required for M10.

If an explicit `--output` option is later approved during implementation, it MUST remain secondary to the standard timestamped retention model and MUST NOT create overwrite risk by default.

### 6.5 Prohibited Inputs

The PDF Report Interface MUST NOT accept or introduce:

* `--target`
* Port selection
* Domain selection
* Probe selection
* Timeout tuning
* Credential inputs
* Authentication inputs
* Remote host inputs
* URL inputs
* External API inputs
* Risk scoring options
* Severity options
* Enrichment options
* Correlation options
* Inference options
* Discovery execution options

### 6.6 Local-Only Artifact Handling

The interface MUST consume local filesystem artifacts only.

The interface MUST NOT retrieve input from:

* HTTP or HTTPS URLs
* Cloud storage APIs
* Network APIs
* Databases
* Message queues
* Remote services
* External enrichment platforms

If the operating system resolves a provided path through a mounted filesystem, the PDF Report Interface MUST NOT independently initiate network communication or remote API activity.

## 7. Input Artifact Model

### 7.1 Authoritative Input Artifact

The authoritative input artifact for M10 is the current single-execution structured JSON output artifact:

```text
discovery_run.json
```

This artifact is produced by the existing governed discovery execution and Output / Reporting process.

Earlier development iterations may have produced similarly purposed runtime artifacts under names such as `run_results` or `network_report`.

The current governed runtime output filenames are:

```text
discovery_run.json
discovery_report.md
```

M10 consumes one existing `discovery_run.json` artifact at a time and produces one corresponding timestamped PDF rendering.

M10 does not define a cumulative execution log, historical run registry, or multi-run comparison model.

### 7.2 Required Top-Level Structure

The input artifact MUST be a JSON object containing the governed run output structure produced by the existing framework.

The expected top-level elements are:

* `context`
* `findings`
* `events`

### 7.3 Context Handling

The `context` object MUST be treated as read-only.

The PDF Report Interface may display context fields such as:

* `target`
* `run_started_at`
* `source_host`
* `assumptions`
* `run_id`

The interface MUST NOT alter, normalize, enrich, suppress, or reinterpret context values.

### 7.4 Findings Handling

The `findings` list MUST be treated as read-only and authoritative.

Each finding record MUST be displayed in a way that preserves:

* `domain`
* `category`
* `target`
* `evidence`
* `observed_at`
* Any additional governed fields present in the input artifact

The interface MUST NOT:

* Modify finding records
* Create new finding records
* Remove finding records
* Deduplicate finding records
* Merge related finding records
* Reclassify finding records
* Infer new meaning from finding combinations
* Treat overlapping findings as duplicates
* Treat one domain’s finding as authoritative replacement for another domain’s finding

### 7.5 Events Handling

The `events` list MUST be treated as read-only and authoritative.

If events are present, they MUST be displayed or included in an appendix.

If no events are present, the PDF may state that no events were recorded, provided this is derived only from the input artifact.

The interface MUST NOT suppress error events or reinterpret them as findings.

### 7.6 Unknown or Additional Fields

If the input artifact contains additional fields not explicitly known to the PDF interface, implementation must handle them deterministically.

Approved handling options are:

* Preserve and display additional fields in a supplemental raw artifact section; or
* Fail closed with a controlled unsupported-artifact error.

The implementation MUST NOT silently ignore additional governed data where doing so would obscure the source artifact contents.

### 7.7 Input Artifact Immutability

The input artifact MUST NOT be modified.

M10 validation MUST confirm that the source `discovery_run.json` file remains unchanged after PDF generation.

## 8. Output Artifact Model

### 8.1 Generated Output Artifact

The generated M10 output artifact is a timestamped PDF report.

The preferred filename format is:

```text
discovery_report_YYYYMMDD_HHMMSSZ.pdf
```

Example:

```text
discovery_report_20260706_171245Z.pdf
```

When written to the preferred output directory, the artifact path would be:

```text
pdf_reports/discovery_report_20260706_171245Z.pdf
```

### 8.2 Output Artifact Status

The PDF artifact is a human-readable interface artifact.

It is not:

* A new discovery output model
* A replacement for `discovery_run.json`
* A replacement for `discovery_report.md`
* An authoritative technical source of truth
* A governed finding source
* A semantic normalization layer
* A correlation layer
* An inference layer

### 8.3 Output Directory

The PDF Report Interface MUST write PDF reports to a dedicated output directory.

The preferred default directory is:

```text
pdf_reports
```

The implementation MAY allow the operator to specify a different local directory with:

```bash
--output-dir <directory>
```

The output directory model is preferred over a fixed output filename because it supports report retention and reduces accidental overwrite risk.

### 8.4 Timestamped Naming

The PDF Report Interface MUST generate standard timestamped PDF names using UTC.

The timestamp format MUST be compact, filesystem-safe, and deterministic in structure:

```text
YYYYMMDD_HHMMSSZ
```

The timestamp used for the PDF filename SHOULD be derived from the source JSON run context timestamp where available.

Preferred source:

```text
context.run_started_at
```

If `context.run_started_at` is unavailable or invalid, implementation MUST fail closed unless a fallback behavior is explicitly approved and documented.

Using the run timestamp instead of wall-clock PDF generation time improves traceability to the source discovery execution and avoids unnecessary nondeterministic output naming.

### 8.5 Filename Collision Handling

If a generated timestamped PDF path already exists, the interface MUST fail closed by default.

The interface MUST NOT silently overwrite an existing PDF.

If collision-handling suffixes are later approved during implementation, they MUST be deterministic and documented.

The minimal approved M10 behavior is fail-closed collision handling.

### 8.6 Output Path Safety

The interface MUST validate that:

* The output directory path is provided or defaults to an approved local directory
* The output directory exists or is created in a controlled manner if approved during implementation
* The output directory is writable
* The generated output artifact has a `.pdf` extension
* The generated output file does not already exist
* The generated output path does not conflict with the input path

The interface MUST NOT create unrelated directories, modify unrelated files, or perform cleanup outside the requested output artifact path.

### 8.7 Generated Artifact Version-Control Handling

Generated PDF reports are local run artifacts.

Generated PDFs SHOULD NOT be committed to version control unless intentionally promoted as approved validation evidence.

Routine PDF outputs should be handled consistently with existing generated discovery output artifact controls.

## 9. PDF Retention Model

### 9.1 Retention Objective

M10 improves practical human-readable report retention by producing timestamped PDF artifacts.

This allows multiple PDF reports to coexist in the same PDF output directory.

Example:

```text
pdf_reports/
├── discovery_report_20260706_141500Z.pdf
├── discovery_report_20260706_151233Z.pdf
└── discovery_report_20260706_171245Z.pdf
```

### 9.2 Retention Boundary

The M10 retention model applies to generated PDF artifacts only.

M10 does not redesign the retention behavior of:

* `discovery_run.json`
* `discovery_report.md`
* Existing discovery execution output behavior
* Existing `wauig-discovery --output-dir` semantics

### 9.3 Audit Value

The PDF retention model provides:

* Human-readable report history
* Timestamped artifact naming
* Easier operator review
* Easier portfolio demonstration
* Reduced accidental PDF overwrite risk
* Traceability to the source run timestamp

### 9.4 Source JSON Authority

Even though timestamped PDFs support report retention, the source `discovery_run.json` remains the authoritative technical run artifact.

The PDF SHOULD include enough raw or near-raw source content to support review, but it does not replace the source JSON artifact as the governed technical source of truth.

## 10. PDF Rendering Model

### 10.1 Rendering Principle

PDF rendering MUST be deterministic, local, and presentation-only.

The PDF renderer may format, paginate, wrap text, and organize sections for readability, but MUST NOT alter governed data meaning.

### 10.2 Minimum PDF Content

The generated PDF SHOULD include the following sections:

1. Report title
2. Source artifact reference
3. Run context
4. Findings register
5. Events register
6. Raw findings appendix
7. Rendering limitations / authority statement

### 10.3 Source Artifact Reference

The PDF SHOULD identify the input artifact name or provided input path in a local-only manner.

The PDF MUST NOT embed sensitive local environment metadata beyond what is explicitly provided by the operator or already present in the source JSON artifact.

### 10.4 Run Context Section

The Run Context section SHOULD display the source JSON `context` values without alteration.

The section may include:

* Target
* Source host
* Run started timestamp
* Run ID
* Assumptions

### 10.5 Findings Register

The Findings Register MUST include every finding from the input artifact.

The register SHOULD preserve input order unless a deterministic alternate presentation order is explicitly approved and documented.

Each displayed finding SHOULD include:

* Finding index
* Domain
* Category
* Target
* Observed timestamp
* Evidence summary or evidence block
* Any additional governed fields present in the source finding

### 10.6 Raw Findings Appendix

The PDF MUST include a raw or near-raw finding appendix sufficient to trace each displayed finding back to the source JSON content.

The appendix may format JSON for readability, but MUST NOT remove, rename, suppress, normalize, alias, or reinterpret fields.

Deterministic JSON key ordering may be used for stable display if no keys or values are altered.

### 10.7 Events Register

If events exist, the PDF MUST include them in a dedicated section or appendix.

Events MUST remain separate from findings.

The interface MUST NOT convert events into findings or findings into events.

### 10.8 Permitted Presentation Aids

The following presentation aids are permitted when deterministic and traceable:

* Page headers
* Page numbers
* Tables
* Section headings
* Record indexes
* Literal record counts
* Text wrapping
* Controlled truncation only if the full value is also available elsewhere in the PDF

Record counts may describe only the number of records present in the source artifact. They MUST NOT be framed as risk, severity, coverage, exposure completeness, or posture scoring.

### 10.9 Prohibited Presentation Behavior

The PDF renderer MUST NOT:

* Hide findings
* Merge findings
* Deduplicate findings
* Prioritize findings
* Score findings
* Rank findings
* Reclassify findings
* Infer posture
* Infer risk
* Infer service correctness
* Infer protocol correctness
* Infer authentication state
* Infer product identity
* Infer exploitability
* Infer exposure completeness
* Reconcile overlapping generic and specialized findings
* Treat PDF section membership as authoritative exposure semantics

### 10.10 PDF Metadata

PDF metadata MUST be controlled to the extent supported by the selected dependency.

The PDF generator MUST NOT intentionally embed:

* Local usernames
* Unapproved hostnames
* Absolute local paths unless already provided as input
* Dynamic generation timestamps
* Environment-specific metadata
* External resource references
* JavaScript
* Embedded active content

If the PDF dependency automatically inserts volatile metadata, implementation must either disable it, normalize it, or document the limitation and validate deterministic visible report content.

## 11. Dependency Governance

### 11.1 Dependency Need

A third-party PDF generation dependency is acceptable for M10 because the existing project produces JSON and Markdown artifacts but does not currently include a governed local PDF rendering capability.

The dependency is permitted only to support local PDF rendering of existing governed JSON output.

### 11.2 Dependency Decision Status

This specification does not approve a specific package by name.

Final dependency selection is deferred to M10 implementation and must be documented as part of the implementation activity.

### 11.3 Approved Dependency Selection Criteria

Any proposed PDF dependency MUST satisfy the following criteria:

* Compatible with the project’s supported Python runtime
* Suitable for local PDF generation
* Does not require network communication during PDF rendering
* Does not require authentication
* Does not retrieve external templates, fonts, scripts, stylesheets, or resources at runtime
* Does not perform discovery, scanning, probing, enrichment, inference, correlation, or target interaction
* Does not introduce dynamic plugin loading for report behavior
* Has a license acceptable for internal enterprise use
* Has a dependency footprint that is minimal and reviewable
* Allows deterministic rendering behavior to the greatest extent practical
* Allows generated report content to be produced from local input only
* Can be declared explicitly in packaging metadata
* Can be validated in a clean virtual environment

### 11.4 Package Declaration Expectations

If a third-party PDF dependency is approved during implementation, it MUST be declared explicitly in packaging metadata.

The expected implementation-time package metadata impacts may include:

* Adding the approved PDF dependency to `pyproject.toml`
* Adding a separate console script entry point for the PDF interface
* Preserving the existing `wauig-discovery` entry point
* Preserving the existing project source module list unless a governed packaging change is approved
* Avoiding unnecessary dependencies

No package metadata changes are made by this specification.

### 11.5 Dependency Validation Expectations

M10 validation MUST confirm that the selected dependency:

* Installs successfully in a clean virtual environment
* Supports local PDF generation from a governed `discovery_run.json`
* Does not require runtime network access
* Does not alter source JSON data
* Does not introduce discovery, inference, correlation, orchestration, control, or reporting business logic
* Does not introduce unauthorized target interaction
* Does not require credentials
* Does not require external services
* Does not introduce nondeterministic visible report content under identical input conditions

### 11.6 Boundary Controls Preventing Dependency-Driven Scope Drift

The selected dependency MUST NOT be used to justify:

* HTML dashboard implementation
* Web service implementation
* Remote template retrieval
* External API integration
* Data enrichment
* Risk scoring
* Finding normalization
* Finding suppression
* Finding reconciliation
* Runtime discovery execution
* Target interaction
* Authentication handling
* New output semantics for existing JSON or Markdown artifacts

If the dependency requires capabilities outside local PDF rendering, it must be rejected or formally reviewed through governed change control.

## 12. Runtime Position and Execution Ordering

### 12.1 Post-Processing Position

The PDF Report Interface executes only after a governed discovery run has already produced `discovery_run.json`.

Approved flow:

```text
wauig-discovery
→ discovery_run.json
→ wauig-report-pdf
→ pdf_reports/discovery_report_YYYYMMDD_HHMMSSZ.pdf
```

### 12.2 No Orchestrated Runtime Position

The PDF Report Interface has no position in the orchestrated discovery module order.

It MUST NOT be registered before, between, or after existing runtime modules.

It MUST NOT consume `prior_findings` through the orchestrator.

It MUST NOT emit findings back into the orchestrator.

### 12.3 Existing Runtime Ordering Preserved

The existing runtime module ordering remains unchanged by M10.

M10 implementation MUST NOT modify existing module registration order.

### 12.4 Independent Invocation

The PDF Report Interface is invoked independently by an operator after `discovery_run.json` exists.

It MUST NOT automatically execute as a side effect of `wauig-discovery` unless a future governed change explicitly approves integrated behavior.

Integrated automatic PDF generation is out of scope for the minimal M10 capability.

## 14. Determinism Requirements

### 14.1 Deterministic Rendering

Identical input artifacts and identical command arguments MUST produce identical visible PDF report content.

### 14.2 Stable Record Ordering

Findings and events SHOULD be rendered in the same order they appear in the input artifact.

If any alternate ordering is approved later, it MUST be deterministic, documented, and validated.

### 14.3 Stable Formatting

Formatting behavior MUST be deterministic.

The renderer MUST avoid adaptive or heuristic behavior that changes report structure based on environment-specific conditions.

### 14.4 Timestamp Handling

The generated PDF filename MUST use UTC timestamp format:

```text
YYYYMMDD_HHMMSSZ
```

The filename timestamp SHOULD be derived from `context.run_started_at` in the source JSON artifact.

This supports deterministic naming tied to the original discovery execution.

The PDF Report Interface MUST NOT introduce dynamic visible timestamps by default.

Timestamps displayed in the PDF SHOULD be limited to timestamps already present in the source `discovery_run.json`.

If implementation later introduces a report generation timestamp, it must be explicitly approved, documented, and reconciled with deterministic validation requirements.

### 14.5 PDF Metadata Handling

Implementation MUST minimize or normalize nondeterministic PDF metadata where supported by the selected dependency.

If byte-for-byte PDF determinism is not practical due to dependency-generated metadata, validation MUST compare deterministic visible report content and document the metadata limitation.

### 14.6 No Randomness

The PDF Report Interface MUST NOT use randomness, generated identifiers, adaptive ordering, nondeterministic grouping, or environment-dependent presentation logic.

## 15. Error Handling Expectations

The PDF Report Interface MUST fail safely and deterministically.

### 15.1 Controlled Error Conditions

The interface MUST produce controlled errors for:

* Missing `--input`
* Input file does not exist
* Input path is not a file
* Input file is not valid JSON
* Input JSON is not a governed discovery run object
* Required top-level artifact structure is missing
* Missing or invalid `context.run_started_at`
* Findings structure is invalid or unsupported
* Events structure is invalid or unsupported
* Output directory path is invalid
* Output directory cannot be created if directory creation is approved during implementation
* Output directory is not writable
* Generated output path already exists
* Generated output path conflicts with input path
* PDF rendering failure
* Dependency import or runtime failure

### 15.2 Fail-Closed Behavior

The interface MUST fail closed for unsupported or ambiguous artifact states.

The interface MUST NOT partially generate a misleading PDF if the source artifact cannot be validated sufficiently for controlled rendering.

### 15.3 No Input Mutation on Error

Input artifacts MUST remain unchanged even when errors occur.

### 15.4 Output Cleanup on Error

If PDF generation fails after partial output creation, implementation SHOULD remove the incomplete output file where safe and deterministic.

If removal is not possible, the interface MUST produce a clear controlled error message identifying that a partial output artifact may remain.

### 15.5 Error Message Boundaries

Error messages SHOULD identify the failing condition without exposing unnecessary local environment details.

Error messages MUST NOT include credentials, secrets, unrelated file contents, or target interaction details.

* M10 does not execute discovery
* M10 does not register as an orchestrated runtime module
* M10 does not modify `DiscoveryFinding`
* M10 does not introduce discovery, inference, correlation, orchestration, control, or reporting business logic
* M10 does not alter JSON or Markdown output semantics
* M10 does not alter existing `wauig-discovery` output filename behavior

### 16.2 Static Boundary Review

Static review MUST confirm that M10 implementation does not import, invoke, instantiate, or modify:

* Discovery domains
* Host Configuration inference logic
* Correlation logic
* DiscoveryOrchestrator execution
* Existing CLI discovery execution path
* Existing output serialization logic in a way that changes semantics

Static review MUST confirm that no socket, networking, authentication, target interaction, or external retrieval behavior is introduced.

### 16.3 Input Read-Only Validation

Validation MUST confirm that the input `discovery_run.json` artifact is unchanged before and after PDF generation.

Recommended validation approach:

* Capture input file hash before execution
* Execute PDF generation
* Capture input file hash after execution
* Confirm hashes match

### 16.4 PDF Output Directory Validation

Validation MUST confirm that the PDF interface writes to the approved output directory model.

Validation MUST confirm:

* PDF output directory is used
* Timestamped PDF filename is generated
* Generated filename uses `YYYYMMDD_HHMMSSZ`
* Generated filename is derived from `context.run_started_at` where available
* Existing PDF files are not overwritten
* Multiple input artifacts with different run timestamps can produce distinct PDF report filenames

### 16.5 PDF Content Validation

Validation MUST confirm that the generated PDF includes:

* Run context from the source JSON
* Every finding from the source JSON
* Every event from the source JSON, where events are present
* Evidence content sufficient to trace back to the source JSON
* A clear statement that the source JSON remains authoritative

Validation MUST confirm that no findings are omitted, merged, deduplicated, reclassified, or semantically reconciled.

### 16.6 Negative Input Validation

Validation MUST include controlled negative tests for:

* Missing input file
* Invalid JSON input
* Missing required top-level structure
* Missing or invalid `context.run_started_at`
* Invalid findings structure
* Existing generated output file collision
* Invalid output directory path

### 16.7 Determinism Validation

Validation MUST execute repeated PDF generation using identical input and identical arguments.

Validation MUST confirm deterministic visible report content.

Where PDF metadata prevents byte-identical output, validation MUST document the metadata limitation and confirm deterministic extracted text or normalized content.

### 16.8 Dependency Validation

If a third-party PDF dependency is approved, validation MUST confirm:

* Clean virtual environment installation succeeds
* Dependency is declared explicitly
* Dependency does not require network communication during execution
* Dependency does not retrieve remote resources
* Dependency does not introduce prohibited behavior
* Dependency behavior remains limited to local PDF rendering

### 16.9 Regression Validation

M10 validation MUST confirm that existing M1–M9 behavior remains unchanged.

Regression review MUST confirm:

* Existing `wauig-discovery` behavior remains unchanged
* Existing JSON output generation remains unchanged
* Existing Markdown report generation remains unchanged
* Existing module registration order remains unchanged
* Existing discovery domains remain unchanged
* Existing inference behavior remains unchanged
* Existing correlation behavior remains unchanged
* Existing controlled vocabularies remain unchanged
* Existing evidence fields remain unchanged
* Existing `DiscoveryFinding` schema remains unchanged
* Existing fixed discovery output filenames remain unchanged unless separately governed
